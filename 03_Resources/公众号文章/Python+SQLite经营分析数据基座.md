# Python + SQLite 搭建经营分析数据基座

作者：某服装公司财务总监，年营收2亿+，4个核心系统数据互不相通。

## 核心问题

| 系统 | 用途 | 数据量 |
|------|------|--------|
| ERP | 销售/采购 | — |
| WMS | 库存 | — |
| CRM | 客户 | — |
| 财务软件 | 费用/应收 | — |
| **合计** | **30万行** | **Excel导出** |

## 为什么要这样做

### 原因一：AI 让动手门槛塌了
以前财务人员搭ETL要两周，ROI算不过来。现在用 Claude Code / TRAE，中文描述需求，AI 写完整代码，**两天搞定**。
> "AI 真正改变的不是'能不能做'，而是'值不值得做'。"

### 原因二：高层根本不用BI系统
- 老板的提问方式是"点对点"的，不是"大而全"的
- BI 仪表盘做了没人打开，老板要的是**30秒内给出准确答案**
- BI 的悖论：谁最需要数据，谁反而没时间看仪表盘

**作者的思路转变**：不建"漂亮的看板"，建一个**"随时能回答老板问题的查询引擎"**。

## 技术架构

### 整体链路
```
Excel源文件（5个文件夹）
    ↓ Python脚本（4个.py文件）
    ↓ SQLite数据库（1个.db文件）
    ↓ 分析查询（直接SQL / Excel连接 / Power BI连接）
```

### 为什么选 SQLite
| 方案 | 部署 | 性能 | 成本 | 适合数据量 |
|------|------|------|------|-----------|
| Excel | 零 | 10万行卡死 | 免费 | <10万行 |
| **SQLite** | **零（Python内置）** | **百万行轻松** | **免费** | **<100万行** |
| MySQL | 需服务器 | 千万级 | 需运维 | 百万~亿级 |
| 数据仓库 | 需团队 | 海量 | 几十万起 | 亿级以上 |

### 星型模型设计

**维度表（10张）** — 描述"谁、什么、哪里、何时"：
- 日期维度（8年日历，含节假日/财年）
- 产品（53个SKU × 5大类）
- 客户（10,493个）
- 城市（129个 × 4大区）
- 渠道、部门、仓库、科目……

**事实表（7张基础表）** — 记录"发生了什么"：
- 销售订单（261,814条）
- 库存快照（月度）
- 采购流水（8,322条）
- 应收账款（3,852张发票）
- 收款流水（4,412条）
- 部门费用（10,607条）
- 预算（收入/成本/费用）

### 打通系统间的"断头路"

1. **建维度表做"翻译官"** — 不同系统的ID通过维度表关联
2. **用视图做"一键汇总"** — 一行SQL搞定跨表分析
3. **预聚合物化表加速查询** — 常用分析口径（预算对比、单品毛利、AR账龄）预先算好

### 自动化更新
```
.bat文件 + Windows计划任务：每天凌晨2点自动执行
python build_db.py --incremental
```
自动检测源文件是否更新，有变化增量加载，无变化跳过。全程无人值守。

## 能回答以前答不了的问题

1. **任意维度的收入下钻**：按年→按大区→按省份→按城市→按品类→按单品
2. **单品级毛利排名**：带销量、收入、毛利、毛利率
3. **应收账龄分析**：按区域/客户/账龄段分布
4. **预算执行率**：一数到底，不需要"等等我拉个透视表"

## 对我们系统的参考价值

### 设计理念
- ✅ **SQLite + Python 路线** — 我们工资系统已经用这个，方向一致
- ✅ **零运维、免安装** — 跟我们的目标一致
- ✅ **查询引擎优于仪表盘** — 这个理念跟我们工资系统的"计算引擎"设计思路相通

### 可借鉴的设计模式
- **星型模型（维度表+事实表）** — 如果我们的工资系统需要跨模块多维度分析，可以参考
- **增量加载机制** — `--incremental` 参数 + 文件变化检测
- **预聚合物化表** — 常用计算预先算好，查询秒出

### 跟我们的区别
- 该方案是**数据仓库/分析**导向，我们的是**业务操作/流程**导向
- 我们的工资系统有**自定义公式计算引擎**，这是该方案没有的
- 但我们已经有 `salary-system-backend` 技能覆盖了这部分
