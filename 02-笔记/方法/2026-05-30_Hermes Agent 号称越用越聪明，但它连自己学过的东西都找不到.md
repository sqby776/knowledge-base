# Hermes Agent 号称越用越聪明，但它连自己学过的东西都找不到

> 来源：https://mp.weixin.qq.com/s/M_HNzSstaNNm_21AsLK7WA
> 提取时间：2026-05-30 21:55:55

---

Hermes Agent 最大的卖点是 learning loop。越用越聪明。自动生成 skill。跨会话记忆。但这个闭环有一个前提。agent 得能找到之前学过的东西。找不到，就学不到。闭环就断了。先理解 Hermes 的记忆架构Hermes 的记忆不是一层。是四层。第一层：热记忆。&nbsp;MEMORY.md（~2200 字符，约 800 token）和 USER.md（~1375 字符，约 500 token）。每次会话开始时注入系统 prompt。不需要检索，不需要工具调用。永远在那里。这是一个刻意的设计：像大脑一样工作，而不是像数据库。小、精选、始终活跃。写入是即时的——agent 在会话中更新文件，立刻落盘。但系统 prompt 不会在当前会话中变化。新写入在下一次会话才生效。这是为了 LLM prefix cache 稳定性。第二层：冷记忆。&nbsp;所有 CLI 和消息平台的会话存储在 SQLite 数据库（~/.hermes/state.db）。FTS5 全文索引。agent 通过&nbsp;session_search&nbsp;工具主动查询。这是问题所在的层。第三层：外部记忆提供者。&nbsp;8 种可选插件——Honcho（辩证用户建模）、Mem0（最快设置）、Hindsight（知识图谱）、Holographic（HRR 代数 + 信任评分）、OpenViking、RetainDB、ByteRover、SuperMemory。只能同时启用一个。内置记忆始终运行。第四层：Obsidian Vault。&nbsp;不是插件，是 skill。agent 写结构化笔记到你的 Obsidian 应用。问题出在第二层FTS5 是什么？SQLite 内置的全文搜索引擎。BM25 排序。匹配的是词，不是意思。你第一次问：「帮我部署 asyncio 服务」。Hermes 解决了。记录在会话存档里。你第二次问：「把那个异步服务跑起来」。agent 调用&nbsp;session_search。FTS5 搜不到。因为「异步服务」和「asyncio 服务」没有共同关键词。换个说法，它就失忆了。一个 Reddit 用户在 r/ClaudeCode 上分享了他为编码 agent 构建记忆系统的经验：❝「搜索是基于关键词的，不是语义的。FTS5 不理解 'database' 和 'DB' 是相关概念。但系统能工作，因为是 agent 构造查询，不是用户。」想了想，这个观点有道理——agent 比人类更擅长构造精确的搜索词。但它也有局限：agent 不知道自己三周前用了什么措辞来描述同一个问题。为什么选 FTS5这不是 Nous Research 的疏忽。是有意的取舍。特性FTS5向量数据库延迟&lt;1ms50-200ms依赖零（SQLite 内置）需要额外服务成本$0$0-70/月离线支持通常不支持备份cp file.db backup.dbAPI 调用精确匹配极强（函数名、错误码）弱Hermes 的设计哲学是「$5 VPS 就能跑」。零外部依赖。一个 SQLite 文件搞定一切。FTS5 完美契合这个约束。亚毫秒级响应。零配置。文件级备份。而且 v0.11+ 加入了启动时自动 prune + vacuum，数据库自维护。代价是：它只懂词，不懂意思。搜「database」找不到「DB」。搜「缓存层」找不到「Redis 延迟」。搜「部署流程」找不到「CI/CD pipeline」。实际影响有多大想象一个场景。你用 Hermes 做了三个月的 K8s 运维。第一个月你说「pod 挂了」。第二个月你说「容器崩溃」。第三个月你说「workload 异常退出」。三种说法。同一个问题。FTS5 把它们当成三个不相关的事件。learning loop 不会把它们关联起来。不会生成统一的排障 skill。Milvus 的工程师做了精确的诊断：❝「当文档只有几百个的时候，这个缺陷可以忍受。超过这个量级，learning loop 就停止学习了——因为它找不到自己的历史。」讽刺的是——用得越久，积累的历史越多，关键词检索的噪音越大。「越用越聪明」可能在某个拐点之后变成「越用越迟钝」。一个 DGX Spark 论坛用户的实测数据：FTS5 在 10000+ 条目上的中位检索延迟是 10ms。速度不是问题。准确率才是。Holographic Memory：一个有趣的尝试Hermes 的 8 个外部记忆提供者中，有一个叫 Holographic。它用 HRR（Holographic Reduced Representations）——一种代数方法表示记忆。不是向量相似度，不是关键词匹配。是代数运算。核心特性：纯本地 SQLite，零 pip 依赖信任评分：反复确认的记忆权重增加，被新信息矛盾的记忆权重下降自我纠正：推向纠正而不是纯累积但有一个 bug（GitHub issue&nbsp;#17350）：如果 numpy 没装，Holographic 会静默降级到 FTS5-only 模式。没有警告，没有错误，hermes doctor&nbsp;也检测不到。你以为在用语义检索。实际上还是关键词匹配。这个 bug 在 v0.8.x 被发现。说明即使有了替代方案，实际部署中的可靠性仍然是问题。修复方案：Hybrid SearchMilvus 2.6 给出了答案。同时跑两种搜索，用 RRF（Reciprocal Rank Fusion）合并结果。搜「asyncio 原理」→ 向量检索命中语义相关内容搜「find_similar_task 函数在哪」→ BM25 精确匹配函数名搜「上次那个异步任务怎么处理的」→ 两者配合社区已经有人用&nbsp;sqlite-vec&nbsp;在本地实现了类似方案。不需要外部服务。仍然是单文件架构。只多了一个 384 维的 embedding 列。一个 DEV Community 的教程展示了 200 行 Python 就能搭建完整的 hybrid RAG：SQLite + FTS5 + sqlite-vec + RRF。保持了「零依赖」的哲学。补上了语义理解的短板。更深的问题检索只是表象。更深的问题是：learning loop 假设「相同的问题会用相同的词描述」。这个假设在以下场景会崩：多语言用户。&nbsp;有时中文问，有时英文问。FTS5 跨语言能力为零。团队使用。&nbsp;A 说「部署」，B 说「发布」，C 说「上线」。Hermes 的 profile 系统是隔离的——每个 profile 有独立的&nbsp;~/.hermes/profiles/&lt;name&gt;/&nbsp;目录。但同一个 profile 内，不同措辞仍然是问题。长期使用。&nbsp;你自己的用词习惯也会变。三个月前你说「跑测试」，现在你说「验证一下」。skill 检索。&nbsp;91 个内置 + 520 社区 skill。当 skill 库膨胀到几百个，靠关键词匹配找到正确的 skill 越来越不可靠。Composio 的博主说得直白：「当 skill 没有在你期望的时候触发，问题几乎总是在 frontmatter 的 description 里。」对比：其他方案怎么做Honcho 辩证建模。&nbsp;不存事实，存推理模式。它建模的是你怎么思考——推理模式、沟通风格、决策倾向。用辩证法（dialectic）在每次对话后推导洞察。支持多轮深度（1-3 轮），自动选择冷启动 prompt（通用用户事实）vs 暖 prompt（会话范围上下文）。这绕过了关键词匹配的问题。因为它不是在搜索「你说过什么」，而是在推理「你是什么样的人」。Hindsight 知识图谱。&nbsp;存储时做实体提取和关系建模。检索时用多策略搜索 + LLM 合成。比 FTS5 强得多，但需要额外服务。kiro-cli 的 knowledge base。&nbsp;支持两种索引——Fast（BM25）和 Best（all-MiniLM-L6-v2 语义搜索）。用户按场景选择。从第一天就提供了语义检索选项。后来才明白——一个学习系统的瓶颈，往往不在「学」的部分。在「找」的部分。你可以有世界上最好的 skill 生成机制。但如果检索系统找不到相关历史，生成机制就永远不会被触发。这就像一个人有完美的记忆力，但索引系统是按字母排序的卡片柜。你记住了一切，但找不到你需要的那张卡片。好消息是，这个问题有解。Holographic memory、Honcho、sqlite-vec + RRF——方案不缺。坏消息是，Hermes 的核心 session_search 仍然是纯 FTS5。外部提供者是可选的、额外的、需要配置的。大多数用户跑的是默认配置。默认配置就是纯关键词。Learning loop 的天花板，就卡在这里。参考资料How to Fix Hermes Agent's Learning Loop with Milvus 2.6 — Milvus Blog[1]Hermes Agent Memory System Explained — Remote
