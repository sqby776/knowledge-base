# 当 AI 开始失忆 Hermes 记忆系统改造手记

> 来源：微信公众号

## 一、五层记忆架构分工

| 层级 | 存储介质 | 用途 | 容量限制 |
|------|----------|------|----------|
| **MEMORY.md** | 本地 Markdown | 当前会话临时偏好/纠正，注入到 system prompt | 小（8,000 字符上限） |
| **Session Search** | 本地 SQLite FTS5 | 会话历史上下文——操作过程、临时状态 | 大但检索能力有限 |
| **Skills** | 本地 Markdown | 验证过的工作流和操作流程 | 按需加载，无硬上限 |
| **Honcho** | 云端向量数据库 | 用户深层画像、行为建模 | 按需 |
| **Mem0** | 云端向量数据库 | 长期数据主存储（新增第五层） | 容量大 |

---

## 二、八大坑与解决方案

### 坑一：Honcho 的越界问题

**问题**：Honcho 的 `hybrid` recallMode 会混淆"用户偏好"与"技术配置"，将 VPS IP、API 端点、Python 环境路径等环境事实错误存入用户画像。

**后果**：Agent 调用 Honcho 时，配置信息被当作"用户背景"注入上下文，占用 token、增加噪音、导致过时信息覆盖正确信息。

**解法**：
- 画红线。明确规定 Honcho 只存两类东西：
  - 行为模式：用户的决策习惯、沟通风格
  - 偏好矛盾：用户在不同场景下表现出的看似矛盾但实际一致的深层偏好
- 所有技术配置、项目进展、环境信息，一律走 Mem0 或 MEMORY.md，严禁写入 Honcho

### 坑二：信息分类的三岔路口

**问题**：五层架构下，信息该往哪放缺乏清晰标准，导致同一信息存在多处且版本不一致。

**分类标准**：

| 层级 | 判断标准 | 典型内容 | 生命周期 |
|------|----------|----------|----------|
| **MEMORY.md** | 每次会话都需要，短期内不变 | 用户沟通风格纠正、活跃项目标识、跨系统红线规则 | 用完即删或 replace |
| **Mem0** | 稳定但不是每次都需要，可语义搜索 | VPS 配置、API 端点、技术方案、模型测试结果 | 容量大，不用精打细算 |
| **Session Search** | 操作过程记录，价值在于"还原当时发生了什么" | 调试过程、会议纪要、临时决策上下文 | 不存提取后的纯事实 |
| **Honcho** | 描述用户这个人，而非环境或项目 | 消费观、VPS 管理风格、学习阶段判断 | 不存 ifconfig 能看到的 |
| **Skills** | 经过验证的可复现流程 | Hysteria2 部署流程、n8n API 维护流程 | 只从成功验证的工作流创建 |

### 坑三：Session Search 的中文搜索缺陷

**问题**：SQLite FTS5 默认 `unicode61` 分词器对中文逐字拆分，导致搜索失效。

| 搜索词 | 预期匹配数 | 实际匹配数 | 原因 |
|--------|-----------|-----------|------|
| 千帆 | ~73 条 | 2 条 | 拆成"千"和"帆"，AND 逻辑 |
| 记忆分层 | ~15 条 | 0 条 | 三个字三个 token，AND 逻辑 |
| honcho 模型 | ~8 条 | 0 条 | 中英混合被当纯中文处理 |

**三层 bug 叠加**：
1. 分词策略错误：应空格分词后 OR 匹配，但代码直接整条查询扔进 LIKE
2. 中英混合处理缺失："honcho 模型"中"honcho"被忽略
3. fallback 触发条件不稳定：FTS5 返回少量结果时不触发 fallback

**应对方案**：
- **短期**：Agent 层面查询预处理——按空格分词后用 OR 重新组合
- **中期**：用 jieba 预分词重建 FTS5 索引
- **长期**：替换 FTS5，改用 Meilisearch 或 Elasticsearch

### 坑四：记忆的一致性维护

**问题**：五层架构运行后出现信息漂移、冲突、冗余。

**具体表现**：
- Mem0 里存着"n8n API Key 有效期到 2026-07-26"，到期后无自动清理
- MEMORY.md 写着"phi-4-multimodal"，后来改成"gemma-3-27b-it"，Mem0 旧版本还在
- 同一 VPS 配置，Mem0、MEMORY.md、Session Search 各存一份

**应对**：
- **规则层面**：在 MEMORY.md 中写入"单一事实源"原则——每类信息只在一个层中作为权威源存在
- **流程层面**：引入 Self-Improving Skill，定期运行 OAPAVR 循环
- **自动化层面**：hermes-daily-check 每日自检机制

**策略**：容忍适度冗余，确保权威源准确——同一信息可出现在多处，但必须有一个明确标注为"当前版本"。

### 坑五：Mem0 SDK 的兼容性陷阱

**问题**：Mem0 Python SDK v2.0.1 新风格 API 存在 `filters` 字段解析 bug。

```python
# 旧风格（正常工作）
client.add("content", user_id=..., metadata=...)

# 新风格（filters 不生效，静默失败）
client.add("content", options=AddMemoryOptions(...))
```

**危险**：数据确实存进去了，但查询永远命中不了，无任何报错。

**解法**：
- 坚持使用旧风格 API，不走 options 对象
- 写入后立即用 `mem0_search` 回查验证
- 沉淀到 `mem0-maintenance` Skill 中作为"已知坑点"

### 坑六：语义搜索批量删除事故

**问题**：用语义搜索结果批量删除时，误删了 12 条核心数据（VPS 配置、API 端点、Python 环境路径等）。

**原因**：语义搜索返回"语义相似"结果，非精确匹配。搜索"测试"可能同时返回"Mem0 测试验证通过"和"百度千帆 API 测试结果"。

**解法**：
- **硬规则**：严禁使用语义搜索结果作为批量删除的依据
- 删除必须使用 add() 返回的精确 memory_id
- 如需"搜索后删除"：搜索 → 人工/Agent 确认每条结果的 ID → 逐条精确删除

**教训**：语义搜索是模糊工具，模糊工具不能驱动精确操作。

### 坑七：Honcho 的静默失效

**问题**：Honcho 静默跳过——`is_available()` 返回 `False`，无报错、无日志、无通知。

**根因**：`honcho.json` 中 `hosts.hermes.apiKey` 字段缺失，SDK 静默返回 False 而非抛错。

**解法**：
- 补全 `~/.hermes/honcho.json` 中的 API Key
- 在 `hermes-daily-check` 中增加 Honcho 连通性检查
- 在 MEMORY.md 中记录 Honcho 配置的正确路径和必要字段

**原则**：静默失败是记忆系统最大的敌人。任何一层记忆如果不可用，系统应该明确告警，而不是悄悄降级。

### 坑八：自动化脚本里的"纸上谈兵"

**问题**：`hermes-daily-check` Skill 设计完美，但源码审计发现 6 个 Bug，其中 3 个 P0（数据安全）。

| 严重级别 | 数量 | 典型问题 |
|----------|------|----------|
| P0（数据安全） | 3 | MEMORY.md 路径写错；写入时缺少 `agent_id`，数据写进 Mem0 但永远搜不到 |
| P1（功能失效） | 2 | `_client` 未初始化就调用；Honcho 健康检查中执行写入操作 |
| P2（体验问题） | 1 | SDK 参考文档缺失 |

**教训**：自动化脚本必须经过审计才能上线，尤其是操作记忆系统这种不可逆资源的脚本。

---

## 三、写入质量决策

**决策**：关掉 Mem0 的自动提取（`sync_turn`），改为会话末尾由 Agent 主动调用 `mem0_conclude` 做显式写入。

```
具体实现：将 sync_turn 方法体清空（直接 return），
所有技术事实的写入路径收束到 mem0_conclude 一个入口。

代价：需要 Agent 自己判断什么值得记
好处：写入质量可控，不会把"你好""谢谢"这种噪音灌进去
```

**本质**：用确定性换覆盖度。宁可漏记几条不重要的信息，也不要让噪音污染语义空间。

## 四、Mem0 的价值评估

### 确定有价值的场景

- **语义检索**：FTS5 搜"百度千帆"匹配不到"ERNIE-4.5-Turbo-VL"，向量空间里它们是近的
- **容量自由**：不用再纠结 MEMORY.md 里的每一条信息该删哪条留哪条
- **跨 Agent 共享**（理论价值）：Mem0 是独立服务，多个 Agent 可访问同一份数据

### 确定性存疑的场景

- **写入质量**：依赖 Agent 的判断力，无兜底机制
- **过期信息**：无自动过期或衰减机制
- **SDK 黑盒**：SDK 行为和文档不完全一致，调试成本高

---

## 五、最终建议

### 引入 Mem0 前的自查清单

1. 你的 MEMORY.md 是否已经反复满到需要调上限？
2. 你的 session_search 中文命中率是否令你痛苦？
3. 你是否在多个 Agent 之间传递相同的上下文信息？

### 五条核心原则

1. **先画红线，再加管道**：引入 Mem0 之前，先明确每层记忆的职责边界
2. **只存用得到的东西**："可能有用"是记忆系统的最大敌人
3. **删除用精确 ID，搜索只用来找东西**：语义搜索是模糊工具，模糊工具不能驱动精确操作
4. **自动化脚本必须审计**：AI 写的代码看起来逻辑通顺，但路径拼错一个字符就是 P0
5. **接受不完美**：多层记忆的一致性维护没有银弹

---

## 六、核心洞察

> Hermes 的原生设计理念——"不是所有东西都配住在系统提示词这个黄金地段"——我们最终通过引入 Mem0 作为第五层，实现了这个理念的规模化。
